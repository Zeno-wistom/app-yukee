## 卡顿与突然跳动：证据、原因、修复

| 调查项 | 实际发现 | 本轮处理 |
| --- | --- | --- |
| 静态背景与DPR | 原版每帧重画1672×941底图、压暗和全屏径向暗角；原输出上限2200宽 | 缓存带视差余量的静态图层；尺寸/源图变更才重建。DPR2及2200上限完全保留 |
| 光晕与像素角色 | 数千次径向渐变构造；角色每显示帧重画低清离屏图 | 同色光晕缓存256×256纹理；角色姿态最多60Hz重画，横移/跳跃仍每显示帧插值 |
| 主线程争用 | CPU采样热点包含Three.js的needsUpdate/setup/renderBufferDirect、React jsxDEV；G03绘制回调本身正常负载约0.3ms | 仅G02/G03游戏/校准中的3D桌面改为空闲10Hz、事件灯效30Hz按需更新，保留灯效响应；G01及主页维持原模式 |
| HUD | 原版`value.complete`导致完成后每个RAF都setHud | 完成态也统一80ms刷新，不反复推动React渲染 |
| 推理 | 原管线在身体订阅期间仍做人脸推理 | 同一视频流保留；身体订阅期间跳过无消费者的人脸推理。键盘演示释放摄像头，不新增模型/线程/流 |
| ResizeObserver | 稳定窗口的测量中画布重置为0，不能认定这是主要瓶颈；原缩放位置按宽度比例恢复 | 观察器只标记尺寸变化，在同一RAF里重设并重绘；按车道相对位置恢复，适应不同宽高比 |
| 帧时钟与掉帧 | 原场景长帧最多吞入100ms，位置可在单帧跨较大距离；短暂unstable时视觉仍推进 | 大于80ms的停顿只推进一个小显示步；暂停、unstable、lost和恢复等待统一冻结显示，不补播丢失时段 |
| 突然跳动 | 目标飞行接入全局相位正弦浮动时会偏移；最终接光跳跃切到全局庆祝跳跃时不连续；完成时底图压暗瞬间从0.13切0.04 | 浮动与庆祝从局部零相位接入；完成亮度700ms渐变。纯逻辑测试直接覆盖两个连接点 |
| 肩/髋信号 | Hark已有110ms滤波，肩/髋可用性改变会改变融合权重；并非全画布重置 | 保留Hark的识别、阈值、迟滞与单步坐姿校准；增加信号切换的显示连续性测试，没有假输入、调低阈值或鼻子计分 |

这里只能证明上述代码路径与自动测量中的改善，不把用户所有现场卡顿都归为同一原因，也不声称已经完全消除任何设备上的掉帧。

## 测量方法与原始记录

- Chrome真实浏览器进程，固定1440×900/DPR1、1920×1080/DPR2；正常CPU与明确标记的4倍CPU压力。所有场景在5176顺序执行，没有并行跑测试。
- 同一套脚本：5秒待机、六次左右键盘输入、5秒完成态。记录RAF帧间隔、FPS、P50/P95/P99、超过25/50ms的帧、Long Tasks、布局/脚本/任务耗时、实际画布尺寸、重置计数与角色位置。
- CPU采样器在计量开始前启动、计量冻结后结束，启动/序列化开销不计入游戏帧。早期探索采样曾受这两段开销污染，最终表格仅使用修正后的 `baseline-final` / `optimized-final` 数据。
- 绘制回调测量通过测试脚本包裹实际RAF回调；不把低成本的绘制提交时间冒充完整GPU耗时。另用2200×1238的相同合成场景绘制+强制readback测量渲染工作负载，保留原始JSON。
- 摄像头附加测量：真实本地MediaPipe，使用Chrome合成空视频，在校准页观察检测调用数和耗时；不注入人体关键点，不冒充真人识别。
- 重复测量存在系统负载波动，普通场景常接近120Hz上限。主要比较CPU负担、压力场景和长帧，不用接近上限的零点几FPS差异夸大提升。
